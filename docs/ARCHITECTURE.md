## 0. 全局视图

一条用户消息的完整生命周期（节点名取自 `domain.NodeName`，图的定义在 `workflow/graph.py`）：

```
① 用户问题 + 会话历史
        │
        ▼
② resolve      指代消解：把"那它能退吗"补成一句独立能看懂的话
        ▼
③ classify     意图识别（9 类）+ 槽位抽取（订单号 / 地址 / 原因 / 商品）
        ▼
④ route        条件边：9 类意图 → 5 个出口（graph 上只有 5 条边）
        ├── knowledge       → retrieve → gate ─┬─ 通过 → generate
        │                                      └─ 不通过 → handoff
        ├── business_tool   → agent(ReAct) ──────→ generate
        ├── high_risk       → high_risk_flow ─┬─ 有确定答复 → generate
        │                                     ├─ 业务拒绝需复核 → handoff
        │                                     └─ 缺槽位 → [interrupt] 挂起，用户补充后原地继续
        ├── handoff         → handoff
        └── (fallback)      → retrieve（同 knowledge）
        ▼
⑤ generate / handoff   汇合到唯一的出口，格式与埋点只实现一次
        ▼
⑥ flywheel     仅 handoff 路径：落问题池 + 当时的检索快照
        ▼
⑦ END（+ trace / usage / path / errors 全部留在 AgentState 上）
```

**依赖注入是这张图可测试的前提。** `GraphDeps`（`workflow/graph.py`）显式持有 `llm / resolver / classifier / retriever / gate / self_eval / tools / flywheel / settings / checkpointer`，节点只从 `deps` 取实现，绝不自己 `build_xxx()`。这样测试可以只替换其中一环，评估可以只替换 `retriever` 跑消融，而图本身一行不动。

## 1. 为什么是 Workflow + Agent 混合，而不是纯 Agent

### 三种架构的失败模式对比

| 架构 | 谁决定"下一步做什么" | 失败模式 |
| --- | --- | --- |
| 纯 Workflow | 开发者（状态机） | 话术僵硬；稍微换个说法就答不了；无法处理开放表达 |
| 纯 Agent | 模型（每步自由选择） | **失败模式不可枚举** —— 你没法用测试证明"模型不会心软" |
| 混合（本项目） | 能枚举的交给图，需要理解的交给模型 | 剩下的失败模式可枚举、可测试 |

### 核心矛盾：客服场景里有"不可协商"的动作

退款、退货、取消订单、改地址这四件事，做错了**真的要赔钱**。纯 Agent 做法（把所有业务规则写进 system prompt 让模型遵守）有一个致命弱点：prompt 里的规则会被模型用"帮用户一次"的善意绕过去，而工具里的规则不会。更糟的是，这种绕过程序上不可检测 —— 它表现为"回答得特别友好"。

本项目的分工（四处具体落点）：

| 环节 | 交给谁 | 代码位置 |
| --- | --- | --- |
| 走哪个出口 | Workflow（`INTENT_TO_EXIT` 静态表） | `domain.py` / `nodes.py::route_by_exit` |
| 能不能退款 | Workflow（工具里的确定性规则） | `tools/business.py::request_refund` |
| 缺订单号怎么办 | Workflow（中断追问，不猜不编） | `workflow/high_risk.py::missing_slots` |
| 怎么把"24 小时"说清楚 | Agent（话术） | `nodes.py::make_generate_node` |

### "模型只能提议，不能执行"是怎么实现的

`nodes.py::make_agent_node` 里有一道显式拦截：

```python
# 高风险工具不允许 Agent 直接调用 —— 只能由 high_risk_flow 决定。
if action in deps.tools.high_risk_actions():
    calls.append(ToolCall(name=action, args=..., ok=False,
                          error="HIGH_RISK_REQUIRES_FLOW"))
    break
```

注意这不是"提示模型不要调"，而是**物理上不给这个能力**：模型的名字叫出来了，系统回它一条失败记录并终止循环。同时 `business.py` 里三个高风险工具的 `_ok()` 返回体都带 `"requires_human_approval": True`，`cancel_order` 甚至只返回 `resulting_status: "cancelled"` 而不是直接改状态 —— **工具越权先把状态写死，就是"模型一句话就把单删了"**。

### 可预测的成本

纯 Agent 的成本上限取决于模型的自觉。本项目每一处循环都有硬上限：

- ReAct 循环：`settings.agent_max_steps = 6`（`GraphDeps.max_agent_steps`），超了写入 `errors: ["agent: 达到最大步数上限"]` 并收手 —— 不抛异常。
- 摘要：只在"即将滑出滑窗的新增轮次 token > 2000"时触发一次。
- 工具：`tool_timeout_s = 5.0` / `tool_max_retries = 2`（`tools/registry.py`）。
- 高风险子流程：**零模型调用**，是一条线性状态机。

### 不这么做会怎样

- **纯 Agent 方向**：模型承诺一个不符合政策的退款。而"模型答应了退款"这件事在用户侧是不可撤回的 —— 用户会截图，客服主管会问为什么系统说可以退。事后审计只能看到一段语气友好的对话，找不到任何"哪条规则被绕过了"的证据，因为规则本来就不在代码里。
- **纯 Workflow 方向**：用户说"这单我不想要了"，关键词表里没有"不想要了"，系统答不上来。而"不想要了"正是 `cancel_order` 的典型口语说法 —— 这类表达穷举不完，必须有模型兜底。
- **不做成本上限**：模型可以一直在"再查一个工具"里打转，一次请求能烧掉几十次调用，而用户只是问了个物流。这在按 token 计费的场景下是真实的财务风险。

## 2. 九类意图 → 五出口的收敛为什么重要

### 这张表是全流程最重要的数据结构

`domain.INTENT_TO_EXIT`（9 项）：

| 意图 | 出口 | 成本结构 |
| --- | --- | --- |
| `order_query` / `logistics_query` | `business_tool` | 检索 0 次 + 工具 1~N 次 + 生成 1 次 |
| `product_faq` / `policy_faq` | `knowledge` | 检索 1 次 + 生成 1 次 + 自评 1 次 |
| `refund_request` / `return_request` / `cancel_order` / `change_address` | `high_risk` | 检索 0 次 + 工具 0~2 次 + **模型 0 次** |
| `human_handoff` | `handoff` | 模型 0 次 |
| （分类降级） | `fallback` → 实际走 `knowledge` | 同 knowledge |

### 收敛带来三个具体好处

**① 成本可以按出口统计，而不是按意图。**
五条边 = 五种成本结构。如果按九类意图分别建成本模型，你会得到九套几乎一样但细节不同的估算，而且每加一类意图就要再建一套。按出口统计意味着"这个月高风险出口花了多少钱"是一个可以直接聚合的数字。

**② 相同的业务流程只开发一次。**
四条高风险意图共用 `workflow/high_risk.py::run_high_risk_flow` —— 一套槽位检查、一套中断/恢复、一套工具拒绝话术、一套"哪些拒绝该转人工"的判定（`ESCALATE_TO_HUMAN`）。如果四条各写一套，最后一定会演化出行为不一致（"退款要订单号但取消不要"这种没人能解释的差异）。

**③ 图上只有五条边，新增意图不用改图。**
`nodes.py::route_by_exit` 是一张 5 项 dict：

```python
return {
    Exit.KNOWLEDGE: "retrieve",
    Exit.BUSINESS_TOOL: "agent",
    Exit.HIGH_RISK: "high_risk_flow",
    Exit.HANDOFF: "handoff",
    Exit.FALLBACK: "retrieve",
}.get(exit_, "retrieve")
```

### 不这么做会怎样

- **加一类意图就要动一次图的结构**：图会随业务线性膨胀，每次改图都要重新验证所有既有路径的回归。
- **成本报表维度爆炸**：九类意图 × 五种策略（mock/真实 LLM × 检索策略……）的交叉表没人会看。
- **四套高风险流程各自演化**：某天运营发现"改地址不用二次确认，退款要" —— 而这只是两段独立代码的偶然差异，不是一个业务决定。
- **出口不收敛的隐藏代价**：`fallback` 这个出口是刻意保留的第五个。分类失败时走它，而它和 `Exit.KNOWLEDGE` 一样落向 `retrieve` —— 这决定了"系统判不出意图"时的行为是**去检索并让闸门裁决**，而不是直接放弃。`nodes.py` 里那句注释写得很直白：*"答不上来"比"直接放弃"更有用；真正的兜底由闸门在检索之后决定。*

## 3. 置信度闸门为什么必须卡在生成**之前**

### 签名里没有 `answer`，这是刻意的

```python
class ConfidenceGate:
    def check(self, question, retrieval, intent=None, slots=None) -> GateDecision:
```

**没有 `answer` 参数，不是还没写到。** 全部输入都是"检索阶段就已经拿到的东西"：零模型调用、零副作用、微秒级。它便宜到可以每次请求都跑，也贵到没它就要出事。

### 顺序不同，代价差一个数量级

| | 先判后答（本项目） | 先答后判 |
| --- | --- | --- |
| 最坏结果 | 多发一次转人工 | 用户读到了一段没有依据的话 |
| 幻觉是否送达 | 从未发出 | **已经送达，撤回不存在** |
| 补救方式 | 无（不需要） | 追加一句"以上仅供参考" |
| 成本 | 0 次模型调用 | 1 次生成 + 1 次自评 |

「以上仅供参考」这句话在客服场景里几乎没有意义 —— 用户已经相信了那个"24 小时"，并且会拿着它去申请退款。

### 判据逐条可解释（`checks` 字典）

事故复盘时要能指着某一条说"是它拦下来的"：

| 判据 | 含义 | 为什么需要它 |
| --- | --- | --- |
| `top_score` | 全部召回里的最高分（归一化到 0~1） | 最直观的"有没有底气" |
| `evidence_count` | 分数**过阈值**的证据条数 | 召回总会返回 top_k 条，哪怕库里毫无相关内容，"最不像无关"的那条也会被返回 |
| `score_margin` | 最高分与次高分之差 | 衡量"有没有第二条独立证据印证同一个结论" |
| `entity_coverage` | 问题里的关键实体（品类/时间/金额）在有效证据里出现的比例 | 分数高但答非所问，靠这条拦 |
| `avg_score` | 有效证据的平均分 | 区分"一条独苗"和"一片全都够格" |
| `recalled_count` | 未经阈值过滤的召回条数 | 分辨"没召回"还是"召回了但都不够格"（只作审计） |
| `threshold` | 本次实际生效的阈值 | 调参后能证明配置真的生效了（只作审计） |

### confidence 的算法与它背后的三个判断

```
base       = 0.40*top_score + 0.30*margin_score + 0.30*count_score
confidence = base * (0.70 + 0.30*entity_coverage)
```

**① `margin_score` 不直接用差值，而是过一道饱和映射 `m/(m+0.25)`。**
差值本身没有绝对意义：精排分差 0.2，在一种打分口径下是"碾压"，在另一种口径下是"五五开"。判相对量级比判绝对值稳。`_MARGIN_SCALE = 0.25` 意味着 margin 等于 0.25 时 `margin_score` 恰好 0.5。

**② `count_score` 用对数增长（`log1p(n)/log1p(3)`，3 条饱和），不用线性。**
第 2 条证据的价值远大于第 4 条 —— 从 1 到 2 是"有了交叉印证"这个**质变**。线性增长会奖励"召回一堆"而不是"召回得准"。`_COUNT_SATURATION = 3`。

**③ 单条证据时 margin 封顶 0.35，不是 0 也不是 1。**
只有一条证据时 `margin` 恒为 0（`_margin()` 显式返回 `0.0`，注释写明：*"margin 的语义是"第二名离第一名多远"，只有一条时这个问题的答案是"没有"，数值就该是 0，而不是一个看着挺大的假差距"*）。但 `_confidence()` 里还额外封了一层 `_SINGLE_EVIDENCE_MARGIN_CAP = 0.35` —— 因为别处（离线评估脚本）可能绕过 `_margin` 直接传 margin 进来，而"单条证据 = 无交叉印证"这个结论**不该依赖调用方把参数传对**。

**④ 实体折价系数下限是 0.7 而不是 0。** 实体覆盖不足时闸门**不该自己拒**，拒答原因要由 `low_coverage` 这条规则单独给出，原因才可解释。折价只负责把 confidence 压下去，让下游（高风险审核、飞轮优先级）也跟着谨慎一点。

### 拒答规则的顺序即优先级

```python
if not raw:                      → NO_EVIDENCE     "知识库里没有检索到…"
elif top_score < threshold:      → WEAK_EVIDENCE   "相关性只有 0.28（低于 0.35）…"
elif len(valid) < min_count:     → WEAK_EVIDENCE   "够格的资料不到 1 条…"
elif cov_pairs and coverage < 0.5: → LOW_COVERAGE "资料里没有覆盖到：生鲜…"
else:                            → 通过
```

顺序是有意义的：**先报"一条都没有"，再报"有但都不够格"，接着"够格但太少"，最后才是"够格但不贴题"**。这样用户拿到的解释永远是最贴近根因的那一条，而不是"最先撞上的那条"。

这里还藏着一个容易写错的地方：`top_score` 取的是**全部召回**里的最高分，不是有效证据里的最高分。这两个数只在"至少有一个人过线"时才相等，而它们不等的那种情况恰恰最需要区分开：

- `raw` 为空 → 库里真的没有 → `no_evidence`
- `raw` 不空但全不过线 → 有声噪但不足以回答 → `weak_evidence`

把这两种都算成 `no_evidence`，会把"知识缺失"和"检索没做好"混为一谈 —— **而飞轮上这两种问题的处理方式完全不同（一个补文档，一个调检索）。**

### 不这么做会怎样

- **生成之后再判**：`RefusalReason.SELF_EVAL_FAILED` 会被大量触发。这条路径确实存在于本项目（`nodes.py::make_generate_node` 里那道自评），但它的定位是**兜底**：*"它拦不住已经发生的幻觉，但能拦住"即将发出去"的那一次"*。把自评当主力 = 每次幻觉都要先付出一次生成成本，还要赌自评能发现它。
- **只有 top_score 一个判据**：库里内容少时，任何问题都会召回出 top_k 条，且最高分那条看起来都不低（"最不像无关"的那条）。没有 `evidence_count` 过阈值过滤，噪声会被当成证据。
- **闸门用模型实现**：把"最便宜的一道检查"变成"第二贵的调用"，而且引入不确定性 —— 同一个输入两次运行给出不同的通过与否，消融实验就全废了。
- **闸门自己抛异常**：闸门崩了就等于闸门不存在。"检测幻觉的组件自己把自己搞挂"是最没面子的一种故障。所以 `check()` 外面包了一层 try，降级路径的 `checks` 键位与正常路径**完全一致** —— 下游读 `checks["top_score"]` 时不该因为这次走了降级路径就 `KeyError`。*"兜底"和"兜底并保持一致"是两件事。*

### 一个被消融数据揭出来的依赖：闸门需要"绝对分数标尺"

`no_answer` 桶（60 题，知识库里没有答案）的拒答准确率实测是：

| 策略 | 拒答准确率 |
| --- | ---: |
| dense | 0.0000 |
| sparse | 0.9833 |
| hybrid | 0.0000 |
| hybrid_rerank | **1.0000** |

这不是评测 bug。除精排外的三条策略，证据分都来自 §5 里那个相对归一化（`raw_score / prior_max`）—— **"本查询最好的一条"恒等于 1.0**，必然 ≥ 阈值 0.35，所以分数判据永远不触发。`sparse` 能到 0.9833 是因为那批问题在 BM25 侧零词面命中（`s > 0` 过滤后无证据）→ 走 `no_evidence`。

**结论：精排除了"把对的排到前面"，还提供了闸门赖以工作的绝对分数标尺。** "要不要上精排"因此不只是效果问题 —— 没有精排的绝对分，生成前闸门就只剩"有没有召回"这一条判据可用了。这是"先判后答"能否成立的前置条件之一，也是消融表里最值得讲的一格。

## 4. RAG 切分为什么按标题层级 + 表格结构

### 核心主张

> **一条规则被从中间劈开，模型只看到半个条件，就会给出错误答案。**

### 具体例子（`data/knowledge/退款政策.md` 的生鲜小节，逐字引用）

```markdown
## 生鲜类

生鲜类商品（蔬果、肉禽、水产、乳品、冷冻食品）不适用七天无理由退款，
只受理**品质问题**退款，且必须在签收后 24 小时内提交，同时上传商品照片。

生鲜类商品的退款比例如下：

| 商品状态 | 申请时间窗 | 退款比例 | 是否需要寄回 |
|---|---|---|---|
| 已签收且有品质问题 | 签收后 24 小时内 | 100% | 否 |
| 已签收且有品质问题 | 签收后 24 至 48 小时 | 50% | 否 |
| 已签收且部分变质 | 签收后 24 小时内 | 80% | 否 |

超过 48 小时才反馈品质问题的生鲜订单，原则上不予退款，由客服视情况发放等值优惠券作为补偿。
```

注意这段结构上有三个"必须一起看"的部分：**正文的条件（24 小时内必须提交）→ 表格的三档比例 → 段末的兜底（超过 48 小时不予退款）**。三者合起来才是一条完整规则。

定长滑窗（比如每 500 字一刀）会发生什么：切点很可能落在表格与"超过 48 小时"之间，或者把正文与表格拆开。用户问"生鲜 48 小时还能退吗"，检索到正文 chunk 的模型看到的是：

> 生鲜类商品不适用七天无理由退款，只受理品质问题退款，且必须在签收后 24 小时内提交…

它会回答："生鲜类需要签收后 24 小时内提交退款申请。" 这句话漏掉了"24 至 48 小时可退 50%"，也漏掉了"超过 48 小时不予退款但可补偿优惠券"。用户得到的是一个**比真实政策更严格**的答案（本该能拿回 50% 却被告知不能退），或者——如果切分把表格整块切走而只留下正文——会得到**比真实政策更宽松**的答案。**半个条件是错误答案，不是不完整的答案。** 而且它读起来完全通顺，没有任何可察觉的错误信号。

### 切分的四层规则（`retrieval/chunking.py`）

1. **标题是天然边界**：`#`~`######`，跨标题绝不合并、也绝不切开。维护一个面包屑栈，遇到 n 级标题就截到 n-1 级再压入。跳级标题（H1 直接到 H3）用空位补齐层级 —— 否则面包屑会错位到错误的父节点上，**溯源就是假的**。
2. **表格是原子单位**：整张表一个 chunk，含表头。拆了就丢列头，单元格变成孤儿（"生鲜 | 24小时 | 需照片" 脱离表头后完全读不懂）。同时 `table` 字段保留二维结构，`KbChunk.prompt_text()` 渲染时补回表头。
3. **只有小节正文超长（`DEFAULT_MAX_CHARS = 800`）时才在段落边界细分**，且**单个段落再长也不切**（`_pack_paragraphs` 的注释：*"宁可这一块超标，也不要在一句话中间断开 —— 那句被断开的话往往正是"24 小时后不予受理"这样的条件句"*）。
4. **代码块整块跳过结构解析**：里面的 `#` 和 `|` 都是字面量，不能被当成标题或表格（`_FENCE_RE`）。

### 两个配套细节

**`chunk_id` 用 `doc_id#序号`（四位补零），不用内容哈希。** 理由是可读、可定位（"退款政策#0004 就是生鲜那张表"），且在**文档内容不变**时天然稳定 —— 评估集里写死的 `expected_chunk_ids` 因此不会随重建索引而失效。用内容哈希的话，改一个错别字就会让整份评估集的标注全部对不上。

**`doc_id` 的来源只有一处定义**：`chunk_document_file()` 用文件名（不含扩展名）。`load_from_dir()` 和评估脚本必须用同一套规则，否则 `expected_chunk_ids` 对不上 —— 这就是为什么这个入口被单独抽出来。

### 实测数据（本机真实运行）

| 文档 | chunk 数 | 其中表格 chunk |
| --- | ---: | ---: |
| 会员与优惠.md | 11 | 3 |
| 发票与售后.md | 16 | 5 |
| 商品与尺码.md | 13 | 5 |
| 物流与配送.md | 10 | 3 |
| 退款政策.md | 12 | 3 |
| 退货政策.md | 8 | 2 |
| **合计** | **70** | **21** |

### 不这么做会怎样

- **定长滑窗**：见上面的生鲜例子。这是"看起来能跑、偶尔答错、错了还很有道理"的典型 —— 最难发现的一类缺陷，因为输出是通顺的。
- **表格拆开**：用户问"生鲜类退款比例是多少"，检索到的单元格是"24"或"48"，脱离表头后模型不知道这个数字单位是什么，很容易答成"生鲜超过 24 天"。
- **chunk_id 用内容哈希**：评估集标注全部失效，于是"检索效果"这个指标变成一次性的、不可回归的。
- **切分不保结构，只按长度**：BM25 的文档侧会丢掉标题里的限定词。所以 `_bm25_doc()` 刻意把 `title`、`breadcrumb`、表格内容一起并入分词文档 —— *"表格里的数字恰恰是用户最常问的（"退多少比例"）"*。

## 5. 双路召回 + RRF 为什么优于加权求和

### 两路各自补什么

| 路 | 实现 | 擅长 | 短板 |
| --- | --- | --- | --- |
| 稠密 `dense` | `MockEmbedder`（确定性哈希词袋）/ `bge-m3` | 同义改写、语义相近 | 专有名词、订单号、"24 小时"这类精确串匹配 |
| 稀疏 `sparse` | `rank_bm25.BM25Okapi` + jieba 分词 | 关键词精确命中、罕见词 | "退钱"匹配不到"退款" |

### 为什么是 RRF 而不是加权求和

```
RRF:  score(d) = Σ_r  w_r / (k + rank_r(d))
```

**① 免归一化，这是最硬的理由。** 稠密的余弦分挤在 0.6~1.0，BM25 的分可以是 0~30 的任意值，两者**分布形状不同**。min-max 归一化会被单个离群点带偏；z-score 要求分布近似正态（BM25 的分布长尾严重）；按查询归一化会让"这一路的绝对把握"这个信息丢失。RRF 直接扔掉分数、只看排名，**天然免疫量纲问题**。

**② 鲁棒，不需要随数据分布重调参数。** 加权求和需要为每一路调一个归一化方案和一组权重，而这些参数会随知识库规模漂移 —— 换一批文档就得重调一次。RRF 只有一个 `k`，且它的作用有清晰的语义解释。

**③ `k=60` 让"多路都靠前"胜出，而不是"某一路的第一名"。**
`k` 压住"第 1 名和第 2 名"的差距。这正是要的性质：**两路都排第 3 的文档，通常比只有一路排第 1 的更靠谱** —— 前者被两个独立的检索信号同时确认。

### 实现里两个刻意的确定性处理

- **k 必须 ≥ 1**（`k = max(1, int(k))`）：k=0 时 rank=0 会除零，且"第 0 名"的权重趋于无穷，融合退化成"取第一路的第一名"，失去融合的意义。
- **分数相同时按 id 升序**：*"否则并行测试会随机失败，消融实验的表也会对不上。"*
- **同一路内重复 id 只按最好名次计一次**：重复出现往往意味着数据有脏，让它重复加分等于放大脏数据的权重。

### 分数口径的转换（一个容易踩的坑）

RRF 的绝对分是 `1/(k+rank)` 量级的小数（约 0.016），直接当置信度用会**永远低于闸门阈值 0.35**。所以 `pipeline.py` 做了相对归一化：

```python
score = round(raw_score / prior_max, 6) if prior_max else 0.0
```

归一化成"相对本查询最好一条"的比例分，阈值 0.35 这类配置在语义上才稳定。精排之后 `score` 被替换成精排分（`rerank_score` 同时保留原始分）。

### 顺带：为什么 Milvus 一个库扛两路

`MilvusVectorStore`（`retrieval/stores.py`）的价值在于 **Milvus 2.5+ 内置 BM25 函数**：插入时由服务端自动从原文生成稀疏向量，一个 collection 同时扛稠密和稀疏。这省掉"再引一套 Elasticsearch 来跑 BM25"的运维 —— 少一个需要独立部署、独立监控、独立扩容的组件，也少一处"两套系统的数据不同步"的故障源。

而默认的 `MemoryVectorStore`（numpy 矩阵 + 余弦）**不是"临时方案"**：单机知识库几万条 chunk 时，numpy 矩阵点积（几毫秒）比一次带网络的向量库往返还快。工程上够用就是对的。

### 实测：四策略消融（`eval/artifacts/ablation.json`，300 题 × 5 桶各 60）

| 策略 | Recall@5 | MRR | HitRate@5 | Precision@5 | P50(ms) | 拒答准确率 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| dense | 0.8743 | 0.7951 | 0.9625 | 0.2375 | 0.2 | 0.0000 |
| sparse | 0.9181 | 0.8624 | 0.9792 | 0.3100 | 0.1 | 0.9833 |
| hybrid | 0.9181 | 0.8522 | 0.9833 | 0.2533 | 0.3 | 0.0000 |
| **hybrid_rerank** | **0.9389** | **0.8914** | **1.0000** | 0.2592 | 5.2 | **1.0000** |

每一步的增量都读得出来：

- **双路融合的增量**：`dense` → `hybrid`，HitRate@5 0.9625 → 0.9833，Recall@5 0.8743 → 0.9181。这就是"为什么不用单路"的数字证据。
- **精排的增量主要不在召回，在排序位置**：`hybrid` → `hybrid_rerank`，HitRate@5 0.9833 → **1.0000**，MRR 0.8522 → 0.8914，但 Recall@5 只从 0.9181 → 0.9389。也就是说精排的价值是"把对的排到最前面"（这直接决定 `score_margin` 和闸门的判断），而不是"把没召回的捞回来"。
- **代价**：P50 从 0.3ms → 5.2ms（mock 精排）。相对一次 LLM 调用可以忽略，但它说明精排不是免费的。
- **拒答准确率的巨大反差值得单独读**：只有 `hybrid_rerank` 拿到 1.0000，`dense` / `hybrid` 都是 0.0000。原因见 §12 第 2 条 —— 这不是评测 bug，而是"相对归一化的分数无法支撑绝对阈值"的直接后果。

分桶（`hybrid_rerank`）：`fact_lookup` 1.0000 / `multi_condition` 0.8750 / `multi_turn` 0.8806 / `table_lookup` 1.0000（Recall@5）。**分桶才看得出短板**：事实查询和表格已经满分（说明切分保住了表结构），而"多条件"和"多轮指代"是下一个要攻的方向 —— 前者对应切分边界，后者对应 `nlu/coreference.py`。

指代消解的单独对照（`multi_turn` 桶）：

| 做法 | Recall@5 | MRR | HitRate@5 |
| --- | ---: | ---: | ---: |
| 消解后再检索 | 0.8806 | 0.8317 | 1.0000 |
| 半截话直接检索 | 0.8222 | 0.7554 | 0.9333 |
| **增量** | **+0.0584** | **+0.0763** | **+0.0667** |

这是"指代消解这一层值不值"的直接答案：不消解，这一桶的 HitRate@5 掉 6.7 个百分点，MRR 掉 0.0763。

### 不这么做会怎样

- **只做稠密**：用户打错别字、或问一句包含精确订单号/金额的问题，向量检索可能匹配到语义相近但数字不同的条款 —— 这在退款时效这种问题上是危险的。
- **只做 BM25**：用户说"东西坏了能退钱吗"，知识库里写的是"商品存在质量问题可申请退款"。"退钱" vs "退款"、"东西" vs "商品" 都匹配不上。
- **加权求和 + 手工调参**：消融表会变成"我们调了一版权重，看起来变好了"，而不是"RRF 在四种策略里最好"。前者无法复现，后者可以。
- **不做归一化直接用 RRF 分当置信度**：闸门会把所有问题都拒答（分数永远低于阈值），系统看起来"特别安全"，实际上是坏的。

## 6. 双层上下文（滑窗 + 摘要）的取舍

### 为什么不能只有一层

| 方案 | 问题 |
| --- | --- |
| 全部历史进 prompt | token 成本随轮数**线性增长**；越靠后的信噪比越低（寒暄占比升高） |
| 只留最近 N 轮 | 最早的几轮往往携带"订单号 / 结论 / 用户诉求"，第 10 轮模型突然失忆 |
| 全部压成摘要 | 摘要过的文字**没法做精确匹配**，而指代消解要靠字面替换 |

所以分两层：近处 `window_turns = 3` 轮保原文，更早的压成**一段可增量更新的摘要**，成本从 O(轮数) 降到 O(1)。

### 三个非平凡的实现取舍

**① 滑窗必须切在轮边界上。** `_tail_window()` 以 **user 消息为轮起点**（一次 user 到下一个 user 之前），而不是"每 2 条一组"。真实会话里会出现工具消息、system 提示、连续两条 assistant，按固定步长切会在这些位置切歪 —— 而且是那种**"大部分情况对、偶尔错一轮"的难查错误**。

**② 摘要必须增量，且 prompt 分两段呈现。**

```
【已有摘要】<上一轮的摘要>
【本次新增轮次】<这次新滑出滑窗的轮次>
【要求】请把以上内容压缩成一段简洁的中文摘要…必须保留：订单号、金额、商品名、用户诉求、已经给出的结论；可以丢弃：寒暄和重复表述。
```

分成两段的意义：模型只需要做一次**合并压缩**，而不是把全部历史重新读一遍。两个标记都是模块级常量（`PREVIOUS_HEADER` / `NEW_TURNS_HEADER`）并被测试引用 —— *"段名一改，测试会立刻炸，而不是悄悄退化成"每次都全量重摘"这种看不见的浪费"*。

触发判据只看"还没被摘要、又即将滑出滑窗"的那部分（`newly_older`）—— 已经压过的内容不重复计费，成本才不随轮数增长。

**③ 覆盖范围只信绝对下标，且必须"没有越界"。**

`_coverage_index()` 只认内部状态里记的绝对下标，**不拿 `summarized_turns + len(window)` 去反推** —— 后者只在"每次滑出的轮数正好等于窗口长度"时才成立，窗口还没长满或阈值没触发时会算多，进而把实际没被摘要的轮次**永久跳过**（静默的信息丢失）。`0 < covered <= older_len` 这条判据是流式场景的天然不变式；一旦历史被截断/回滚，它立刻失效并**强制重摘** —— 这正是要的那道护栏。

### 可度量：ContextBundle 的三个字段

`summarized_turns` / `token_estimate` / `summary_generated` **单独抽成一个 Pydantic 模型而不是拼字符串**，目的是让"省了多少 token、丢了几轮"可以被度量：

- `estimate_tokens()` 的公式逐字对齐 `llm._rough_tokens`（含末尾 +1 常量，近似代表单条消息的角色名和分隔符开销）。**口径必须一致**：否则"摘要省了多少 token"这个数字在 mock 记账和本模块记账之间对不上，度量本身就没有可信度。
- `estimate_bundle_tokens()` 只算摘要 + 滑窗，**不算被滑出且未摘要的轮次** —— 那些确实没发出去。这个数字就是"省了多少"的分子。

### 边界处理

- `append()` **不修改传入的 list**（调用方拿着的 history 可能正被另一条分支读，原地 append 会制造难查的幽灵 bug），且历史长度有上限（`max(window_turns * 20, 60)`）—— **没有上限的会话列表是内存泄漏**，"用摘要换长度"仍然会在内存里留下全量历史。
- 摘要失败 / 空摘要一律降级成"无摘要 + 完整滑窗"，并且**降级得到的空摘要不能当作"已覆盖"的证明**（`trusted=False`），否则早期轮次会被永久跳过摘要。

### 不这么做会怎样

- **只截断**：用户在第 1 轮说了订单号，第 8 轮说"那它能退吗"，指代消解拿不到实体，`missing_slots` 报缺订单号，系统伸手向用户要一个他三轮前就给过的单号。用户的反应是"我刚说过啊"。
- **全量保留**：10 轮对话后每次请求都带上 10 轮的全部原文，成本线性增长且每次都要重新读一遍寒暄。
- **全量重摘**：每轮都把全部历史重摘一遍 —— 表面上是"摘要"，实际成本仍然是线性的，而且每次摘出来的内容都不完全一样（模型非确定性），会话状态开始漂移。
- **用 `summarized_turns + len(window)` 反推覆盖位置**：窗口没长满时算出偏大的覆盖下标，早期轮次被永久跳过摘要。这是**静默的信息丢失** —— 只有在用户抱怨"我不是说过吗"的时候才会被发现。

## 7. 高风险子流程的中断 / 恢复

### 场景

```
用户：我要退款
系统：可以帮你申请退款。请把订单号发我（形如 ORD-1007）…   ← 流程在这里暂停，而不是编一个订单号继续
用户：ORD-1007
系统：（从暂停的位置继续）订单 ORD-1007 的退款申请已提交，审核通过后 1 到 3 个工作日退回原支付方式。
```

### 朴素做法 vs interrupt + checkpointer

| | 朴素做法（存成一次问答，第二轮重跑全流程） | `interrupt()` + checkpointer |
| --- | --- | --- |
| 检索 | 第二轮重复检索 | 状态原样在，不重跑 |
| 模型调用 | 第二轮重复消解/分类 | 不重复 |
| 意图漂移风险 | 第二轮"ORD-1007"可能被分类成别的意图 | 停在 `high_risk_flow`，意图不会丢 |
| 实现复杂度 | 低 | 中（要管 thread_id 和落盘） |

### 实测输出（本机真实运行）

```python
graph, deps = build_default_graph(checkpointer=make_sqlite_checkpointer("ck.db"))
cfg = {"configurable": {"thread_id": "t-1"}}

graph.invoke(new_state(..., question="我要退款"), cfg)
# interrupt: {'prompt': '可以帮你申请退款。请把订单号发我（形如 ORD-1007），我先确认一下这笔订单的状态和时效。',
#             'missing': ['order_id']}

graph.invoke(Command(resume="ORD-1007"), cfg)
# path   : ['resolve', 'classify', 'high_risk_flow', 'generate']
# answer : 订单 ORD-1007 的退款申请已提交，审核通过后 1 到 3 个工作日退回原支付方式。
```

### 两个关键设计

**① 没挂 checkpointer 时不允许挂起。**
`nodes.py::make_high_risk_node` 会检查 `deps.checkpointer`：`interrupt()` 在没有 checkpointer 时会直接抛异常，把整条请求打成 500。所以没挂时的正确行为是**把追问当作答复返回**（`handoff=False`, `answer=interrupt_prompt`）—— 用户的诉求没被满足，但他明确知道下一步该给什么。

这个判断显式地从 `GraphDeps.checkpointer` 读（`build_graph()` 编译时把 `checkpointer` 写回 `deps`），而不是让节点自己回想"我编译时挂了没"。

**② 槽位必须来自用户当轮明说的内容。**
`high_risk.py::extract_order_id()` 只吃当轮文本，**不扫历史**。文件 docstring 写得很清楚：

> 如果用正则去历史里"扫"订单号，上一轮讨论过的订单会被当成这一轮的 —— 用户说"我要退款"（本轮无订单号）时，系统会拿上轮的订单**直接退款**。

`tests/test_workflow.py:291` 有一条测试专门钉这件事：`assert out["tool_calls"] == [], "绝不能拿上一轮的订单号去执行退款"`。

### 流程本身是线性的（零模型参与）

```python
missing = missing_slots(intent, question, slots)
if missing:
    return FlowOutcome(interrupted=True, missing=missing, tool_calls=[], interrupt_prompt=...)
# 退款：request_refund
# 退货：get_order → request_refund（两步有顺序："还没发货"和"已签收 40 天"要给的答复完全不同）
# 取消：cancel_order
# 改地址：change_address（缺 address 时同样中断）
```

### 中断状态的落点显式可见

`workflow/state.py::RESUME_TARGETS` 把"补完信息从哪继续"抽成一张表（`missing_order_id → high_risk_flow` / `missing_address → high_risk_flow`），**而不是散落在节点的 if/else 里**。`AgentState` 也单独留了 `interrupt_prompt` / `missing_slots` / `interrupt_resume` / `resume_from` 四个字段。

### 不这么做会怎样

- **编一个订单号继续**：这是最坏的一种。模型看到"我要退款"没有订单号，很容易顺着上下文编一个（或者拿上一轮的），然后真的发起一笔退款。
- **重跑全流程**：第二轮"ORD-1007"这四个字进 `classify`，可能被判成 `order_query`（"订单号 + 数字"是它的强特征），用户等着退款结果却收到一条订单状态查询。
- **无 checkpointer 时强行 interrupt**：整条请求 500。用户说"我要退款"，系统报错。
- **槽位从历史捞**：用户说"我要退款"（本轮无单号），系统拿上轮的 ORD-1007 直接退款 —— **给错误订单退款，比查不到更严重**。

## 8. 数据飞轮为什么必须带检索快照

### 只有两条失败原因吗？不，至少三条

| 快照状态 | 分诊结论 | 该做什么 | 不该做什么 |
| --- | --- | --- | --- |
| `evidences` 为空 | `backfill_kb` | 补文档 / 补 FAQ | —— |
| `top_score < 0.35` | `tune_retrieval` | 调 embedding / 精排 / 阈值 | **补文档完全无用** |
| `top_score >= 0.35` 却没通过 | `review_answer` | 查生成与闸门判据 | 别动检索侧 |
| `retrieval_snapshot is None` | `unknown` | 先修"为什么没存快照" | —— |

代码在 `flywheel/feedback.py::triage_hint()`。

### 为什么不能用"重跑一次检索"代替快照

**审核时知识库已经变了。** 重跑出来的是今天的现场，不是当时的现场。具体后果：如果这期间有人往知识库里补了文档，重跑就会召回出证据 → 分诊结论变成 `review_answer`（"检索没问题"）→ 而**当时的真实原因是"知识库里没有"**。于是这条记录被处理成"看看生成哪里出了问题"，运营永远不会去补那篇真正缺失的文档。

另一个原因：会话上下文没了。原始问题可能是"那它能退吗"，重跑这句半截话的结果和当时消解后的问题完全不同。

### 落池时的三条数据规则

1. **同题去重、`ask_count` 累加。** 人工审核是稀缺资源，100 条记录里有 60 条是同一个问题，就必须先审那一条。去重键是问题的**归一化文本**（`normalize_question()`：全角转半角 → 转小写 → 删所有标点和空白）。删标点而不是规范化标点，因为"运费怎么算"、"运费怎么算？"、"运费怎么算。。。"在业务上是同一个问题。**优先用 `resolved_question`**：半截话的原文千奇百怪，拿原文当键几乎永远命中不了。
2. **`pending()` 按 `ask_count` 降序，并列时按 `(created_at, record_id)` 再排。** 前者是运营优先级，后者是确定性 —— *"没有它，并列的记录顺序取决于 dict 的插入顺序，同一份数据在两次运行里能排出两个顺序，"确定性"就没了。"*
3. **快照只补空、不覆盖。** 第一次落池的现场才是现场，后来的重复提问（可能因为当时知识库已经更新过）盖掉它，就等于把证据毁掉。

### 分诊必须与入口分类分开

`FlywheelSource` 只有 3 个取值，`RefusalReason` 有 6 个 —— 这是故意的。`missing_slot`（缺订单号）和 `high_risk_unapproved`（高风险待批）也会落成 `refused`，因为它们对用户而言同样是"没拿到答案"。**但它们不是知识侧问题**：写一百篇文档也解决不了"用户没给订单号"。所以 `is_knowledge_candidate()` 显式把它们排除，`stats()` 里也单独统计 `refused_process_side` 和 `triage` 两个数字 —— 后者直接决定下一周的工作安排（"该写几篇文档" vs "该调几轮检索"）。

`to_kb_chunk()` 的 `chunk_id` 由**归一化问题哈希**得来（不看 `record_id`），配合 `mark_backfilled()` 的幂等闸门，保证跑两次回灌脚本不会让知识库翻倍 —— `ask_count` 20 的问题不会变成 20 条重复 FAQ。

### 不这么做会怎样

- **没有快照**：所有答不上的问题都被当成"缺知识"去写文档。结果文档越写越多，检索还是捞不出来 —— 因为真正的问题是 embedding 或阈值。这是数据飞轮最常见的失败形态：**看起来在努力，实际在错误的方向上加投入**。
- **每次都新建记录**：同一个问题被问 60 遍就有 60 条待审记录，人工审核队列被同一条问题挤满，真正的新问题排在后面。
- **回灌不做幂等**：审核人为了修一句话把同一条记录审了几次，向量库里就出现多份内容略有差异的同一问题，检索时互相挤占 top-k。
- **不区分流程问题**：分诊表里混进"缺订单号"，"该写几篇文档"这个数字虚高，运营去写文档，而用户在等的只是一个追问。

## 9. 什么时候才轮到微调

### 决策顺序：Prompt → RAG → 规则 → 微调

三个问题，答案都是"能"就别微调：

1. **Prompt 能不能解决？** 改措辞、加 few-shot，成本几乎为零，迭代周期是分钟级。
2. **RAG 能不能解决？** 知识不够就补知识。**别拿模型参数去记事实** —— 参数里的事实无法溯源、无法更新、无法审计，而知识库里的可以（每一条都能给出 `source_path` 和 `chunk_id`）。
3. **规则能不能解决？** 有限类别、关键词明确时，规则比模型更准更便宜，而且是确定性的（可回归测试）。

只有当"任务固定、类别封闭、量足够大、且前三条都试过了"的时候，微调才是对的答案。

### 本项目微调的是什么（以及不是什么）

**不是意图识别。** 9 类意图已经被 LLM + 规则解决了（`nlu/intent.py`，规则通道命中率高到大部分句子零模型调用），再训一个模型是重复投资。

**是 17 类主题分类**（`finetune/dataset.py::LABELS`）：退款进度 / 退款政策 / 退货流程 / 换货申请 / 物流时效 / 物流异常 / 配送范围 / 订单取消 / 地址修改 / 发票问题 / 优惠券使用 / 会员权益 / 尺码咨询 / 材质咨询 / 保修售后 / 支付问题 / 账号安全。

理由是这类分类是**旁路的统计需求**：运营要看"这个月用户在抱怨什么"。它不需要 LLM 的推理能力，只需要又快又便宜又稳定，正是判别式小模型的甜区。**这也正是"什么时候才轮到微调"的示范：不是核心链路，是旁路统计。**

标签里刻意包含语义接近的类别（退款/退货、物流时效/物流异常），用来检验模型是不是真的学到了区别，而不是靠关键词糊过去。

### 为什么 RoBERTa 全参而不是 LoRA

| | LoRA / QLoRA | 全参（本项目） |
| --- | --- | --- |
| 为谁设计 | 7B+ 的模型，全参微调成本高到不现实 | 1 亿参数级别的模型 |
| 做法 | 冻结原参数，只训一小撮低秩矩阵 | 所有参数参与更新 |
| 本项目的成本 | 引入 PEFT 依赖 + 一层额外抽象 | `hfl/chinese-roberta-wwm-ext`，**CPU 十几分钟跑完** |

在这个量级上引入 LoRA 是**增加了一个没必要的抽象，而不是优化**。`TrainConfig.full_finetune` 默认 `True`，`train.py` 里的注释写得很直接："*LoRA 在这里是多余的复杂度 —— PEFT 是为"全参训不起"的大模型准备的，RoBERTa 不在那个量级。*"

### 让结论可信的两个配套

**① 必须有基线。** `baseline_keyword()` 提供一个**不训练**的字符 bigram 最近邻基线。*"没有基线的微调结果是没有意义的 —— "准确率 92%"到底是模型的功劳，还是任务本来就简单？"* `run_pipeline()` 最后输出的 `improvement_over_baseline` 才是微调的价值。

**② 看每类 F1，不只看 Macro-F1。** `_compute_metrics()` 手写混淆矩阵 + 每类 F1（不依赖 sklearn，少一个重依赖且口径自己说了算）。*"只看 Macro-F1 会掩盖"某个类完全没学会"。"* 同时输出 `overfit_gap = train_macro_f1 - dev_macro_f1` —— 差距大就是在背数据。

### 工程上的一个硬约束

`finetune/train.py` **不在模块顶层 import torch**，只在 `_load_torch()` 里延迟导入。这样没装 finetune 可选依赖（2GB 起）的环境仍然能 import 这个模块、跑数据准备和基线，不会因为缺包而整个项目挂掉。同一原则也用在 `observability/tracing.py`（langfuse 延迟导入）和 `retrieval/pipeline.py`（BM25 兜底实现）。

### 不这么做会怎样

- **先微调**：花两周标注 + 训练，得到的模型还不如改两句 prompt。而且一旦业务规则变了（新增一类意图），模型要重新训，而 prompt 改一行就生效。
- **用微调记事实**："生鲜 24 小时"这种知识训进参数里，改政策时你无法定位、无法灰度、无法回滚。
- **没有基线**：报一个"F1 = 0.92"却没有对照，无法回答"这任务是不是本来就简单"。
- **在 1 亿参数模型上用 LoRA**：多一层抽象、多一份依赖，换来的收益接近于零。
- **顶层 import torch**：整个项目在一个没装 torch 的环境里 import 失败，而 finetune 是旁路功能。

## 12. 已知缺口

诚实记录，避免读者按错误预期验证：

1. **业务工具出口的答复是确定性模板，不走模型。** `make_generate_node` 见到 `tool_calls` 就立刻走 `_render_tool_answer`，直接引用工具返回的 `status_label` / `note` 拼话术。好处是不会出现"工具说待付款、模型说已发货"这类自相矛盾；代价是灵活度低 —— 想在答复里加一句安抚话术得改模板而不是改 prompt。这是刻意的取舍，不是缺口。
2. **只有精排策略的拒答准确率是 1.0000，其余三条是 0.0000（sparse 是 0.9833）。** 消融数据（`eval/artifacts/ablation.json`）：`dense` / `hybrid` 的拒答准确率 **0.0000**，`sparse` 0.9833，`hybrid_rerank` 1.0000。原因不是评测 bug：除精排外的三条策略，证据分都来自 RRF 的相对归一化（`raw_score / prior_max`），即"本查询最好的一条"恒等于 1.0，必然 ≥ 阈值 0.35，所以 `no_answer` 桶永远不会被分数拦下；`sparse` 之所以能到 0.9833，是因为那批问题在 BM25 侧零词面命中（`pairs = [... if s > 0]` 过滤后无证据）→ 走 `no_evidence`。**这个对比说明：精排除了排序，还提供了闸门赖以工作的绝对分数标尺** —— "要不要精排"不只是效果问题，也是"闸门能不能工作"的问题。
3. **mock 精排的绝对分在个别查询上仍偏宽松。** 例如"你们在火星有仓库吗"实测 `top_score = 0.3906`（略高于 0.35，因为 "仓库" 与退货流程的片段有字面重叠），而 `low_coverage` 判据因该问题抽不出可加权实体（分母为 0）而跳过。这类边界案例是接真实 embedding / reranker 后需要重新校准阈值的地方。
4. **契约与代码的两处出入**：`CONTRACT.md` §2.F 的图里有独立的 `rerank` 节点，实际没有（精排在 `RetrievalPipeline.retrieve()` 内部）；`domain.NodeName.RERANK` / `TOOL` 两个常量当前未被使用。
5. **会话历史与长期记忆接口没有鉴权。** 演示环境没有登录态，服务层每条读写都带 `user_id` 过滤（`SessionStore` / `MemoryStore` 的 delete/pin 都要求 owner 匹配），但 `user_id` 本身来自查询参数，防不住伪造。真实系统里它必须来自登录态。
6. **`audit_log` 表建了、运行时没有写入路径。** 节点级审计目前只在内存里的 `Tracer`（`/api/trace/{request_id}`），重启后历史请求的调用树就查不到了。表结构本身完整（`tests/test_storage.py` 覆盖）—— 接上落库是下一件该做的事。
7. **长期记忆在 mock 下是规则表抽取**（订单号 / 尺码 / 联系方式偏好 / 会员 / 称呼 / 备忘，7 类模式），自由表述（"我住杭州，一般周末在家"）要等真模型。进 prompt 的是**最近 8 条**、没做相关性排序：条目少时够用，量上来之后这里要换成按当前问题做向量召回。
8. **意图识别的"规则通道覆盖率"是真实盲区，我在评估集上量出了数字。** 检索侧的消融是干净的（上面 §5 那些数字都可复现），但 **意图识别没有进入评估**：`eval/run_eval.py` 只打召回/排序/拒答三组指标，从不读 `golden.jsonl` 里的 `expected_intent` 字段。我手动跑了 `IntentClassifier.classify()` 对 300 题的真实准确率：

   - 全部 300 题：0.3933；只看四桶可答题（240）：**0.4875**。
   - 其中 **50/240 题会翻转"高风险 vs 非高风险"的出边判断**（比如「退款的时间窗从什么时候开始算？」期望 `policy_faq` 被判成 `refund_request`，「一个订单最多能改几次地址？」期望 `change_address` 被判成 `order_query`）。
   - 最大的混淆方向是 `product_faq` / `logistics_query` / `refund_request` → `policy_faq`，因为这几类的题是**刻意把动词关键词改写掉**的"裸名词语义题"（"上装选码主要看哪个尺寸？"），规则层抽不到动作词，只能走 `fallback`（`mode` 直方图：`rule` 108 / `fallback` 163 / `mock` 29）。

   三个结构性的原因，不是三个 bug：

   - **① 评估集的 `expected_intent` 字段被语义重载了。** 对可答题它标的是语义意图（`policy_faq` / `product_faq`），对 `no_answer` 桶它标的是**期望去向**（`human_handoff`×59 / `policy_faq`×1，来源是 `eval/build_golden.py::NO_ANSWER`）。"创始人是谁？"语义上不属于九类里任何一类，却标 `human_handoff`。所以"300 题意图准确率"这个单看是误导性的指标 —— 74/300 的 no_answer 桶不该算进意图准确率。
   - **② 规则通道会因单个短通用名词开门。** 可答题里 94 条是"仅命中一个 ≤3 字词"就 `method="rule"`，其中 34 条判错。`_BASE_W = 0.30`、"会员"两个字命中就 conf=0.6 开门、"电子发票发到哪里？"被 `到哪`（logistics 关键词）劫持 —— 通用词在语义题上既是高速通道的燃料，也是误判的来源。
   - **③ 关键的安全网不在"意图准"，在"问/要分离 + 高风险流程只信当轮槽位"（§7）。** 误判成 `policy_faq` 的代价是答一段政策（可接受）；误判成高风险动作的代价是多一句"请把订单号发我"（保守，不动钱）；真正会动钱的那一步仍由 `run_high_risk_flow` 的确定性规则 + `extract_order_id(question)` 只认当轮文本兜住。所以这是**体验问题，不是资金安全问题** —— 但面试若被问"意图凭什么比检索可靠"，正确答案是"它有真实盲区，靠下游兜底，不靠它自己"。
